## 1. 范围与基线

### 1.1 首版范围

严格按 `PRD.md` §2.1 的三个用途（数值刷新 / 事实骨架 / 缺口提示）与 §8 的 13 条 Out of Scope 执行。**Out 列表里的东西一律不在本计划的工作包内。**

**首版明确不做**（含本次拍板的 Q3、Q8）：

| # | 不做 | 结论 |
|---|---|---|
| 1 | 「删除 / 隐藏」概念功能（Q3） | **首版不做**。它解决的不是纠错问题；纠错走 `PRD.md` §7.5 的标记回路 |
| 2 | 数据源可用性看板（Q8） | **首版不做**。用 `docs/数据源清单.md` 手工记录健康状况；源只有 4 个，看板是过度工程 |
| 3 | 事件解剖类的自动解读 | 永远不做（PRD §8 N3、N4） |
| 4 | 媒体正文采集、OCR、分布式抓取、多用户 | 首版不做（PRD §8 N5、N8、N9、N10） |

### 1.2 首版指标范围（Q7 已定）

**首版只做 4 个指标**，对应世界热点区「数据观察」专题的 4 个概念：

| # | 概念 | 关键指标 | 主源 | 声明的校验手段 | 预期定级 |
|---|---|---|---|---|---|
| 1 | `hotspot.data.pmi-reading` | 制造业 PMI 及分项 | 国家统计局 | **C2 同源多口径互校** | **黄**（单源） |
| 2 | `hotspot.data.social-financing` | 社融存量/增量、M1/M2 | 中国人民银行 | **C1 跨源对照**（FRED） | **绿** |
| 3 | `hotspot.data.yield-curve-inversion` | 10Y / 2Y / 3M 收益率与利差 | 美国财政部 | **C1 跨源对照**（FRED）+ **C3 利差公式复核** | **绿** |
| 4 | `hotspot.data.valuation-percentile` | 指数 PE 历史序列与分位 | 中证指数公司 | **C3 派生公式复核**（分位自算） | **黄**（派生） |

**为什么是这 4 个**（不是为了凑数，每一项都有验证目的）：

| 目的 | 由谁覆盖 |
|---|---|
| 覆盖三种校验手段 | C2 → PMI；C1 → 社融、收益率曲线；C3 → 收益率曲线利差、估值分位 |
| 覆盖两条定级路径 | 绿级 → 社融、收益率曲线；黄级 → PMI（单源）、估值分位（派生） |
| 覆盖"直接采集"与"派生计算" | 直接 → PMI、社融；派生 → 利差、分位 |
| **不依赖任何 L2 非官方接口** | 4 个主源全部是官方机构 |

> ⚠️ **对 PRD §10 Q7 建议值的一处收紧**：原建议里含 `northbound-flow`（北向资金）。本次把它**移出首版**，原因是它依赖非官方接口（L2），而首版应当先用官方源把校验框架立起来，**等框架稳了再接 L2 源**——否则"数据可疑"和"框架有问题"两种故障会混在一起，定位不了。
>
> 若 P-C1 发现 4 个主源中有不可行的，按 §3 的门禁处理（替换或降级，并记录），**不放宽验证要求**。

## 2. 工作包分解（WBS）

量级：**S** 小 / **M** 中 / **L** 大。共 **32 个工作包**，分 6 组。

### SRC 采集层

| 编号 | 工作包 | 内容 | 追溯 | 量级 |
|---|---|---|---|---|
| SRC-1 | 抓取纪律层 | 缓存（URL + 日期）、限速、退避重试、显式超时、User-Agent、每次抓取记录（URL / HTTP 状态 / 时间） | PRD §3.4、NF-C6、NF-C7 | M |
| SRC-2 | 国家统计局 adapter | 按指标与期间读取；处理其 UUID + 时间分片结构 | PRD §3.2 | M |
| SRC-3 | 中国人民银行 adapter | 社融、M1/M2；**无正式 API，需页面适配** | PRD §3.2 | M |
| SRC-4 | 美国财政部 adapter | 国债收益率曲线（日度） | PRD §3.2 | S |
| SRC-5 | 中证指数 adapter | 指数 PE 历史序列（供分位自算） | PRD §3.2 | M |
| SRC-6 | healthCheck | 每个源可判定 `ok / broken`；失败明确报错，不重试超过 3 次 | PRD §3.3 SR4、§4.2 | S |
| SRC-7 | 数据源清单实测记录 | 每源的样例响应、字段说明、结构变化记录（**源准入的唯一依据**） | PRD §3.3 SR5 | S |

### CORE 校验与分级

| 编号 | 工作包 | 内容 | 追溯 | 量级 |
|---|---|---|---|---|
| CORE-1 | Observation 契约 | 字段定义、单位规范表、期间格式、`caliber` 标记（累计/当期、同比/环比、季调） | PRD §6.4、§4.4 | M |
| CORE-2 | 归一化层 | 各源输出 → Observation；单位映射；缺失字段处理 | PRD §4.4 | M |
| CORE-3 | **七层漏斗管线** | F1–F7 依次执行；每层可独立测试；**每层明确标注"丢弃 / 降级 / 报错"** | PRD §4.1–§4.8 | L |
| CORE-4 | 阈值与配置 | `config/{sources,mapping,thresholds,settings}.yaml`；改配置不改代码 | PRD §6.5、§4.5 | S |
| CORE-5 | **交叉校验三手段** | C1 跨源对照 / C2 同源多口径互校 / C3 派生公式复核；每指标声明用哪种 | PRD §3.5、§4.6 | L |
| CORE-6 | **适用性白名单** | 指标→概念→字段三元组；不在表内**即使数据正确也丢弃**；配置错误报错 | PRD §4.7 | M |
| CORE-7 | 分级闸门 | 绿 / 黄 / 红；`level_reason` **必填** | PRD §4.8 | M |

### CAND 候选与合入

| 编号 | 工作包 | 内容 | 追溯 | 量级 |
|---|---|---|---|---|
| CAND-1 | 候选生成 | `Measurement` / `Candidate` / `ChangeSet` 结构与留档 | PRD §6.4 | M |
| CAND-2 | diff 与 `changes.md` | 人审产物：变了什么、依据哪个源、哪里需要人决定；黄级置顶 | PRD §2.2 S2、NF-C11 | M |
| CAND-3 | **apply 合入** | 把采纳的候选写回 `content/*.yaml`，**保持既有格式与 block 顺序** | PRD §4.7、§5.2 | L |
| CAND-4 | 溯源留档 | `observations.json` + 抓取元数据，支持"任一字段反查到 URL/时间/响应" | PRD NF-C7、A-C15 | S |

> ⚠️ **CAND-3 是本计划技术风险最高的一项**。`content/*.yaml` 是人工维护的文件（含缩进、block 顺序、行内 flow-map 写法）。用普通 YAML 库读写会**重排格式、丢注释**，把 diff 变成噪音，还会让"人工审核"失去意义。所以用 `ruamel.yaml` 做保序往返，并**必须有一组"读写往返不改一个字节"的测试**（见 §4.1）。

### P-C1 接口可行性验证 ← **下一步**

| 项 | 内容 |
|---|---|
| 目标 | **先证明能拿到数据，再动手写工具**（顺序不可反） |
| 工作包 | SRC-7；CORE-1 的字段调研部分 |
| 怎么做 | 逐个手测 4 个主源 + 2 个交叉验证源：可用性、返回结构、鉴权、单位、期间表示、发布节奏 |
| 交付物 | `docs/数据源清单.md`：每源的实测记录 + **3–5 个真实抓取样例**（原始响应片段）<br>+ **附录 B 的 13 处示意数据分类清单**（保留示意 / 替换真实） |
| 必跑测试 | ① 每个源至少一次真实成功的抓取并落盘留档<br>② 对每个指标确认"这条数据在源里叫什么、单位是什么、期间怎么表示" |
| 门禁 | **至少 3 个源能稳定取到真实数据**，且每个源有实测记录。<br>若某源不可行 → **替换主源或把该指标移出首版**，并记录结论；**不放宽验证要求** |
| 对应 PRD 验收项 | **A-C1**、G1（分类部分） |

> **为什么这一步不能省**：源可用性是整个方案的地基。若跳过它直接写工具，最后可能发现某个源根本没有可程序化获取的接口——那时已经写了几千行代码。这一步的产出是**一页纸 + 几个真实样例**，成本极低、信息量极高。

## 4. 测试计划

### 4.1 测试类型与归属

| 类型 | 归属 | 说明 |
|---|---|---|
| **单元测试**（无网） | 全程 | 基于**录制的响应 fixture**；不依赖网络（NF-C9） |
| **契约测试** | CORE-1、IND-1、IND-2 | Observation / Feed 的 schema 与 `contractVersion`；破坏性变更必须让测试失败 |
| **往返测试** | CAND-3 | **YAML 读写往返不改一个字节**（除目标字段外）——本计划最重要的一条测试 |
| **快照测试** | CAND-2 | `changes.md` 的形态（含"需要你决定"行、黄级置顶） |
| **违例注入测试** | CORE-3 ~ CORE-7 | 主动构造违例数据，断言**必被拦下**（消融式验证） |
| **集成测试**（真实网络） | SRC-*、P-C1 | 标记为慢测试，**默认不跑**，需要时手动触发 |
| **独立性测试** | IND-4 ~ IND-7 | 词表扫描、diff 证明、无 Node 环境 |
| **人工验收** | P-C3、P-C4 | `changes.md` 是否真的"不打开代码就能读懂" |

### 4.2 硬门禁测试（失败则不允许进入下一阶段）

| 测试 | 阶段 | 为什么是硬门禁 |
|---|---|---|
| **失败不产假数据**：断网 / 源 502 / 结构变化 → 候选数 = 0 且明确报错 | P-C2 / P-C3 | 空的数值比没有数值危险得多，它会被下游当成"数据就是 0"（A-C3） |
| **既有门禁 0 error** 且全库 68 概念、`recipe` 全库唯一 | P-C4 | 爬虫不得为自己开后门（A-C8） |
| **core 零绑定扫描 = 0 命中** | P-C2 / P-C4 | 一旦 core 里出现 `recipe`，工具就永久绑死在 Recall 上（A-C11） |
| **涉及文字的变更必为红级** | P-C3 | 因果解读与结论句是热点区的立身之本，机器不得静默改写（A-C7） |

> 前三条来自 `PRD.md` §9 的硬门禁定义；第四条是本计划新增——因为它是"分级闸门"这个核心机制唯一不能出错的地方。

## 附录：与 Recall 侧的接口施工顺序

爬虫与 Recall 是两个独立仓库/目录，唯一接口是 `flags.json`（`PRD.md` §5.4 A1–A3）。施工顺序建议：

| 顺序 | 谁做 | 做什么 | 何时需要 |
|---|---|---|---|
| 1 | **爬虫** | FB-1 实现"文件不存在时静默跳过" | P-C3 前 |
| 2 | **Recall** | A1 `concept_flags` 表 + A3 导出 `flags.json` | P-C3 前（否则 FB-2 无法真实验证） |
| 3 | 双方 | FB-3 对齐 schema 与默认路径 | P-C3 期间 |

> **可以并行，但有依赖**：P-C3 的 A-C9（待修正标记生效）需要 Recall 侧真能导出文件。若不想等，P-C3 可先用**手工构造的 `flags.json`** 验证 FB-1/FB-2，把真实联调推到 P-C4——**测试不允许跳过，只允许用 fixture 顶替真实文件**。

**Recall 侧的那部分不占本计划的工作包**，由 Recall 自己的 `开发计划.md` 排期（已在根项目 §0 登记）。
